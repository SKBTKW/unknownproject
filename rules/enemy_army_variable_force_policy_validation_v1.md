## 1. 正式原則と今回の境界

正式原則は、Stage1の潜在部隊A/B/C、Aは主力、構成は調査前に確定、TruthからKnownへの一方向観測、構成と制圧力・参加部隊の分離である。A主力は大型種主体を意味しない。本番Generator、Blueprint、Lifecycle、Bootstrap、Truth、Trialは変更していない。Stage1 Trial1の総制圧力20・1参加部隊も変更しない。

今回確認するのは「標準種主体の共通基盤を残し、枠だけから主体種族を決めにくくできるか」である。構成差が迎撃や戦術選択を実際に変えること、調査画面で公開できること、面白いことは未検証であり、本書の分布から断定しない。

## 3. 検証定義

全案にRunSeed 0〜9999、Stage1、10,000軍団・30,000潜在部隊を使用した。各Snapshotを即時再生成して完全一致を確認した。同じSeed集合だがpolicy id/versionは派生系列に含まれるため、案間で同じ一様乱数を引く比較ではない。

種族構成距離はtotal variation distance、すなわち`0.5 × Σ|share左-share右|`（0=同一、1=共通種族なし）。軍団内距離はA-B/A-C/B-Cの平均。軍団間距離はSeed順で隣接する軍団同士をA/B/C同枠で比較した平均で、比較数9,999。この隣接定義と区分は診断用でありGameplayルールではない。

```powershell
node scratch/diagnose_enemy_army_generation_distribution.mjs --models B,C,D,E --count 10000 --start 0 --json
node scratch/diagnose_enemy_army_generation_distribution.mjs --models B,C,D,E --count 10000 --start 0 --markdown
```

同一プロセスで2回生成し、compact JSONへ正規化した完全レポートのSHA256はいずれも `095b8fa1a0425a4acae1fd5acf4d5825a5104af9580fcb33956bd859f7352892`。生成失敗0、再生成不一致0、各案10,000/10,000 replay一致。

## 6. Eの表現制約と保存復元

現行Generatorは`runSeed・stageId・完全policy`から各スロットを独立生成する。単一policy内に「軍団単位で潜在特性を1回選び、全スロットの候補を条件付ける」構造はない。そのためEを本番Generatorへ無理に追加せず、scratch層で以下を行った。

1. 軍団特性を独立した決定的系列で選択する。
2. 特性に対応する完全な既存policyを構築する。
3. 既存Generatorを1回呼ぶ。

Snapshotは最終構成と選択済み具体policy id/versionを保存できるため、現行Lifecycleの保存・復元は構成を失わない。復元時の再抽選も不要。一方、Eの親モデル、特性weight、派生方式は現行Blueprintの正式contractではない。本番採用するならGeneratorやBlueprintを先に変えるのではなく、Stage開始時のpolicy選択責務を持つ小さなService/設定資産として分離し、次をversion管理するのが最小案である。

- 親モデルid/versionと特性選択の派生方式
- 特性id/weightと各特性の完全policy
- 旧セーブは保存Snapshotを優先し、欠落時に再抽選しない規則
- 生成済みSnapshotの具体policy idから特性来歴を監査できる対応表

これにより本番Generator、Blueprint schema、GameState保存形式の変更を避けられる可能性がある。ただし正式採用時に監査情報として親モデルidをSnapshotへ要求するなら、schema変更を別TASKで評価する。

## 7. 調査価値の考察

**① 懸念点・リスク:** Bは勢力像が明快だが同型集中が強い。Cは部隊差を作る一方、B/C枠の固定傾向が調査の代わりになる。Dは枠固定を避けるが、軍団全体を調べる意味が個別3抽選の要約に留まりやすい。Eは軍団傾向と個別差を分けられるが、特性を公開・戦術へ接続する仕様は未決定であり、現時点では単なる隠れ変数である。

**② 対応策・代替案:** 次の候補はE方向を優先し、Dを対照群として残す。軍団全体の主体傾向を知る調査と、個別部隊の逸脱を知る調査を分けられる可能性がある。採用前に、同じ制圧力・盤面で観測可能な差が迎撃方針を変えるか、軍団傾向だけで個別調査を省略できないか、同じ情報から複数の妥当な判断が残るかをプレイ検証する。調査公開率や戦闘補正を本TASKから逆算しない。

**③ 総括判定:** Dは現行Generatorだけで「枠非固定＋可変」を実現し、Bの同型集中を緩和した。Eは軍団内の共通性とRun間差の二層を作り、今回の目的により近い担当者推奨である。ただしEの特性weight・候補・装備比率は正式採用しない。Gameplay価値、世界観上の標準種主体、観測粒度、因果が承認されるまで本番Bootstrapへ接続しない。

## 8. 正式採用前に決める事項

- 標準種主体を世界観上の正式基調にするか。
- DかEか、Eなら軍団特性の数・意味・weightをどうするか。
- 同型部隊、単一種族、極端差をどの頻度で許容するか。再抽選は禁止条件を設けるか。
- 装備構成を軍団特性と相関させるか。個体装備の表現が必要か。
- 軍団傾向と個別構成のどちらを、何回の調査でどの精度まで公開するか。
- 種族・装備差を既存の迎撃・地形・戦術因果へどう接続するか。
- 正式policy asset、selector Service、旧セーブ互換、監査情報の最小contract。
