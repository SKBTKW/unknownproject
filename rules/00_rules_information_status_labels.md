# Rules Information Status Labels

この文書は `rules/` 内の情報を**削除せずに選別・仕分けするための共通ラベル規約**を定義する。

目的は、古い可能性のある情報や未実装情報を消すことではない。
後から読む設計・実装担当が、情報の採用可否を誤判断しないようにすることである。

## 基本原則

1. **未実装 = 廃止ではない。**
2. **現在のコードから未到達 = Legacyではない。**
3. **古く見える = 旧仕様ではない。**
4. 情報は原則として削除せず、状態をラベルで示す。
5. 実装との差異は、設計正本を実装へ合わせて消すのではなく、`RULES_AHEAD` / `PARTIAL` / `INTERNAL_CONFLICT` 等で示す。
6. `LEGACY` / `SUPERSEDED` は、明示的な廃止決定または後発の確定仕様を確認できた場合だけ付与する。
7. 同一ファイル内に状態の異なる情報が混在する場合は、必要に応じて節単位でラベルを付与する。

## ラベル一覧

| ラベル | 意味 | 実装・設計担当の扱い |
| :--- | :--- | :--- |
| `[CURRENT]` | 現行の設計判断として採用されている | 新規設計・実装の根拠として利用可 |
| `[FOUNDATION]` | 他システムが意味論・データ構造を依存する基礎正本 | 高保護。実装差だけを理由に削除・圧縮しない |
| `[REFERENCE]` | 他システム・Presentation・アセット・データ設計の参照情報 | 直接runtime未使用でも保持する |
| `[IMPLEMENTATION_LEDGER]` | 現runtimeの到達点・挙動を記録する台帳 | 設計正本を置換しない |
| `[RULES_AHEAD]` | 正式仕様が実装より先行している | 実装側の未追従として扱う |
| `[PARTIAL]` | 一部のみ実装・接続済み | 実装済み範囲と未接続範囲を分けて読む |
| `[CANDIDATE]` | 採用候補だが未確定 | 自動的に実装根拠としない |
| `[UNRESOLVED]` | 採否・新旧・正本関係が未確定 | 勝手にCURRENT/LEGACYへ寄せず、確認まで保持 |
| `[SUPERSEDED]` | 後発の確定仕様に置換済み | 置換先を必ず併記し、履歴として保持 |
| `[LEGACY]` | 明示的に廃止された旧方式 | 新規実装根拠にはしないが、削除は別判断 |
| `[INTERNAL_CONFLICT]` | rules内部またはruntimeとの間で矛盾 | 解消まで一方を勝手に正本化しない |
| `[PRESENTATION]` | UI・演出・表示に関する案/仕様 | Domain ruleと混同しない |

## LEGACY / SUPERSEDED 判定条件

次のいずれかを確認できる場合に限る。

- 明示的に「廃止」「撤回」「旧仕様」と決定されている
- 後発の確定仕様が置換対象を明示している
- 正本自身に Deprecated / Legacy と、根拠となる決定経緯が記録されている

次は判定根拠にならない。

- 現在のgameから呼ばれていない
- UIに露出していない
- consumerが未実装
- 古い命名が残っている
- 最近変更されていない
- 現runtimeと違う

## 推奨表記

ファイル先頭またはインデックスに以下の形で記載する。

```text
Labels: [CURRENT] [FOUNDATION] [REFERENCE]
```

節単位で状態が異なる場合:

```text
Labels: [RULES_AHEAD] [REFERENCE]
```

## 監査時の扱い

監査担当は、情報を整理するとき次の順序で判断する。

```text
情報を発見
↓
依存先・生成元・生成先・参照先を確認
↓
設計上の採否根拠を確認
↓
ラベル付与
↓
差異を監査記録へ分離
↓
原文は保持
```

削除・大幅圧縮・Legacy降格は、通常の仕分け作業には含めない。
